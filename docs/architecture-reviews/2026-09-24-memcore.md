## Findings

### F1 — MAJOR, fixed: delegation events journaled without classification
`native_provider.on_delegation` called `ingest.append_event` but never `process_event`, so delegation rows sat `pending/unclassified` (11 at 17:24). Subagent payloads contain arbitrary text ("remember this…") and must never be admitted as memory signals.
Fix committed `79a3e3a`: `process_event` now classifies `event_type='delegation'` as `ignore/delegation_operational_event` unconditionally, `on_delegation` processes after append, regression test proves no memory row is created from adversarial delegation text. Both suites green after the fix.

### F2 — MAJOR, cleared: journal backlog reached `operator_attention`, oldest 22 days
Root causes: (a) built-in Hermes `MEMORY.md` mutation events are journaled into MemCore but their target is not a MemCore row → `*_unresolved_target` can never self-resolve (4 events); (b) the semantic queue requires operator decisions by design (no auto-accept) with no periodic review routine; (c) direct inserts outside the plugin path skip the classifier (1 probe event).
Clearance 2026-09-24: 21 events decided — 5 `remember` (private candidates, incl. reports whose source files were deleted from disk), 16 `ignore`/`dismiss`, each with rationale. After: `journal-stats` → `health: ok`, `semantic_review_pending: 0`, `unresolved_builtin_mutations: 0`; doctor hint gone.

### F3 — MINOR: documentation drift
- `integrations/hermes/memcore/README.md:169` claims "83 tests passing"; actual gate is **105**.
- Repository README claims v0.6.0; `plugin.yaml` and plugin doctor report **0.6.1**.
- Repository README badge "243 · Gate_OK" is **accurate** (verified).

### F4 — INFO: plugin doctor reports `0 tool(s), 0 hook(s)` while runtime registers 8 tools
Not a defect: tools are registered through the memory-provider API, not as plugin capability registrations (`memcore-live-hermes.txt:3-4` vs `:31`). The number misleads operators; worth a note in the plugin README or a doctor label change.

### F5 — MINOR, open: recall rendering can cut rows mid-word
Budget is character-based (1200 ch total, whole-item skip); rows >~300 ch could historically be sliced mid-word (MILIM TRSS audit, preserved as candidate `mem-009ea3e03528`). Store rows were shortened data-side on 2026-09-13 (`scripts/shorten_20260913.py`), which hides the symptom; `plugin.py` has no word-boundary/per-row cap yet.

### F6 — INFO: double-write / native-vs-legacy parity question resolved
The exclusive provider registers **0 plugin hooks**, so legacy `pre/post_llm_call` are dead code (SORA TRSS audit, candidate `mem-654004bf3fe3`). The native provider path is the only live writer; SORA traced all 11 private rows to the semantic path. No double-write path exists in the current configuration — provided the plugin stays `kind: exclusive`.

## Recommendations (priority order)

1. **Schedule journal maintenance** — new turns journal every session and semantic review needs operator decisions; without a cadence the backlog regrows. Weekly `journal-stats` + review-queue sweep is enough (~10 min).
2. **Fix doc drift (F3)** — integration README test count 83 → 105; align version strings to 0.6.1.
3. **Word-boundary per-row cap in `build_recall_block` (F5)** — ~220 ch per row, cut on word boundary; small, isolated change with MILIM's before/after numbers as acceptance reference.
4. **Builtin mutation self-resolution (F2a)** — either classify builtin events at append time, or auto-dismiss when the target lives outside the store, to remove the recurring doctor-hint failure mode.
5. Optional: desktop dashboard live smoke (F6/routes) in a future round.
